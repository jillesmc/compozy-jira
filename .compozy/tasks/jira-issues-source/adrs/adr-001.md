# ADR-001: Detect "newly matching" by diffing full key sets

## Status

Accepted

## Date

2026-11-14

## Context

The operator writes free-form JQL. They chose (Q1 = a) that an issue counts as new when it **starts
matching** the JQL and was not seen before. That covers new issues and old issues that move into
the query (status change, assignment, label, time-relative clauses). The GitHub source's model, a
monotonic issue-number watermark, does not transfer. Jira keys are only monotonic per project, and
entry into an arbitrary JQL is not a creation event.

The daemon gives the source an opaque state of up to `max_state_bytes` (default 16 KiB, max 256 KiB),
committed only after a successful check, and a whole-poll deadline (default 30 s).

## Decision

On every poll, list every issue key that currently matches the JQL (keys only). Then compute:

- `new = current − committedSeen`;
- next committed set `= (committedSeen ∩ current) ∪ returned`.

The committed set is stored compactly as a per-project map of issue numbers, tagged with a
fingerprint of `site` + normalized JQL. A missing or mismatched fingerprint makes a quiet baseline.
When the set cannot fit `max_state_bytes`, the poll fails loudly with `source_params_invalid`.

## Alternatives Considered

### Alternative 1: `created` watermark

- **Description**: append `AND created >= "<last check>"` to the JQL, like the GitHub source.
- **Pros**: minimal state; cheap queries.
- **Cons**: misses old issues that move into the JQL, which contradicts Q1. JQL absolute dates have
  minute precision in the API user's timezone, so the boundaries need dedup state anyway.
- **Why rejected**: it does not deliver the chosen semantics.

### Alternative 2: `updated` watermark plus seen set

- **Description**: query `(<jql>) AND updated >= <watermark>` and report keys not yet seen.
- **Pros**: each poll fetches only recently touched issues; scales to huge match sets.
- **Cons**:
  - Issues that already matched before the baseline are reported the first time they are edited,
    unless the baseline lists the full set anyway.
  - Time-relative JQL can start matching without an `updated` change.
  - The seen set grows forever and needs eviction, which causes duplicate reports.
  - It has timezone and minute-precision boundaries.
- **Why rejected**: correctness gaps for exactly the cases Q1 asked for, plus more moving parts.

### Alternative 3: Jira webhooks

- **Description**: Jira pushes events to CompozyOS.
- **Pros**: real time; no polling.
- **Cons**: needs a public endpoint and admin-registered webhooks, and does not fit the check-in
  source contract (pull at check-in).
- **Why rejected**: out of the extension model and the local-first runtime boundary.

## Consequences

### Positive

- Exact "entered the JQL" detection for any JQL, including status moves and time-relative clauses.
- An issue that leaves and re-enters is reported again. That matches "starts matching".
- Keeping only current matches bounds the state, with no eviction heuristics.

### Negative

- Each poll lists the whole match set. A broad JQL costs more requests and time.
- There is a hard capacity limit, about 2,500 keys at the default 16 KiB and about 40,000 at 256 KiB.

### Risks

- Unknown `search/jql` keys-only page size. Mitigation: pagination is correct at any size; S1
  measures it and tunes the guard.
- Poll budget overrun on broad JQL. Mitigation: a 25 s internal budget with a clear error telling the
  operator to narrow the JQL.
